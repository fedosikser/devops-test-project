# Как выполнялась работа

## Исходное состояние

В проекте было Flask-приложение, зависимости, шаблон `.env`, `.gitignore` и
текст задания. Git-репозиторий, Dockerfile и Compose-конфигурация отсутствовали.

## Последовательность

1. Исходное состояние сохранено отдельным коммитом в `main`.
2. Создана ветка `feature/dockerize`; дальнейшие изменения выполнялись только в
   ней.
3. Добавлен multi-stage Dockerfile. Зависимости устанавливаются отдельным слоем,
   а runtime запускается через Gunicorn от системного пользователя `app`.
4. Создан Compose-стек из `web` и PostgreSQL 16. Добавлены внутренняя сеть,
   named volume, healthcheck и ожидание готовности БД.
5. Добавлены `.dockerignore`, безопасный `.env.example` и правила исключения
   локальных секретов.
6. Стек сначала проверен локально: оба контейнера стали healthy, `/health`
   подтвердил подключение к БД, а записи сохранились после `down`/`up`.
7. Создана отдельная Ubuntu 24.04 VM. В ней настроены `deployer`, вход по
   отдельному SSH-ключу, passwordless sudo, Docker, UFW и SSH hardening.
8. Создан публичный GitHub-репозиторий, отправлены `main` и
   `feature/dockerize`, создан Issue #1.
9. Репозиторий заново клонирован с GitHub внутрь VM под `deployer`, выбран
   `feature/dockerize`, создан локальный `.env` с отдельным паролем.
10. Compose-стек собран и запущен внутри VM на гостевом порту 80. С хоста
    приложение проверено через проброс порта 8081 → 80.
11. В VM выполнен полный persistence-тест: после перезапуска ID тестовой записи
    увеличился с 1 до 2.
12. Несекретные результаты проверки добавлены в документацию, после чего открыт
    Pull Request в `main`.

## Трудности и решения

### Docker daemon изначально не работал

Docker CLI был установлен, но локальная VM с Docker Engine была остановлена.
После запуска runtime сборка и Compose-команды стали доступны.

### Авторизация `gh` выглядела недействительной

Проверка из ограниченного окружения вернула ошибку, но прямой запрос
`gh api user` с сетевым доступом подтвердил рабочую сессию. Токен нигде не
печатался и не сохранялся в проекте.

### Повторная загрузка Ubuntu была слишком медленной

На машине уже имелся локальный Ubuntu 24.04 base image. Из него создана
отдельная изолированная Lima VM, поэтому рабочая Docker VM не подвергалась
изменениям безопасности.

### В новой VM отсутствовал рабочий DNS-файл

`/etc/resolv.conf` указывал на отсутствующий файл systemd-resolved. Целевой файл
был восстановлен с DNS-адресом виртуального шлюза, после чего `getent hosts` и
HTTPS-запросы заработали.

### Docker-пакеты в образе были удержаны от обновления

Первая версия provisioning-скрипта всегда пыталась установить Docker заново.
APT остановил операцию, потому что уже установленные пакеты были в состоянии
hold. Скрипт сделан идемпотентным: при наличии Docker и Compose он не меняет
версии, а только включает сервис и продолжает настройку.

### Нельзя закрывать административную SSH-сессию слишком рано

После запрета password login новый вход `deployer` был проверен отдельным SSH
подключением с `BatchMode=yes`. Только после успешной проверки считалось, что
hardening завершён безопасно.

### Секреты нужны для deployment, но не должны попасть в Git

Пароль сгенерирован отдельно и передан в VM через файл `.env` с правами `600`.
`.env`, приватный SSH-ключ и полные временные логи не отслеживаются Git. Перед
каждым push выполнялась проверка списка файлов и поиск характерных сигнатур
токенов и приватных ключей.
